# 프로세스 동기화

프로세스 동기화는 **여러 프로세스(또는 스레드)가 공유하는 자원의 일관성을 유지**하는 것을 목표로 한다.  

대부분의 현대 운영체제에서 문맥 교환은 스레드 단위로 일어나기 때문에 **스레드 동기화**라고도 불린다.

동기화의 필요성은 **경쟁 상태**(Race Condition)와 **임계 구역**(Critical Section)이라는 개념을 이해하는 데서 시작된다.

<br>

## 경쟁 상태(Race Condition)

경쟁 상태는 여러 프로세스나 스레드가 동시에 **동일한 자료에 접근하여 조작**하고, 이때 **접근 순서에 따라 실행 결과가 달라지는 상황**을 말한다.  

쉽게 말해, 다수의 스레드가 동기화 장치 없이 공유 자원에 마구 접근할 때 발생하는 동시성 문제이다.


### 데이터 베이스에서의 경쟁 상태

데이터베이스에 새로운 기본 키(PK)를 생성한다고 해보겠습니다.


```sql
-- 현재 PK 의 최댓값에 1을 더해 새로운 PK 로 사용 
SELECT MAX(PK) + 1 AS NEXT_PK FROM USER;
```

두 클라이언트가 동시에 이 쿼리를 실행하면, 둘 다 같은 최댓값을 조회하고 동일한 새로운 PK를 할당받으려 할 수 있습니다.  

이처럼 **중복된 값을 얻게 되는 상황이 바로 경쟁 상태**입니다.

이런 문제를 해결하기 위해 데이터베이스는 **시퀀스**(Sequence) 메커니즘을 사용한다.  
시퀀스는 트랜잭션 범위 밖에서 동작하며, 여러 클라이언트가 동시에 요청해도 **절대 같은 값을 할당하지 않아** 고유성을 보장한다.

<br>

> 시퀀스가 트랜잭션 밖에서 동작한다는 것은, 값을 가져오면 트랜잭션이 롤백돼도 시퀀스 값은 되돌아가지 않고 그대로 증가한다는 뜻이다.

## 임계 구역(Critical Section)

**임계 구역은 공유 자원(예: 전역 변수, 파일, 데이터베이스 등)을 변경하는 코드의 일부**를 의미한다.  
멀티 스레드 환경에서 고유 자원의 일관성을 유지하려면, 임계 구역에는 **오직 하나의 스레드만 접근하도록 관리**해야 한다.

> 임계 구역은 별로로 정해진 기능이나 공간이 아니라. 기존 코드 중에서 **여러 스레드가 동시에 실행하면 실행 결과에 영향을 줄 수 있는 부분** 특히, **공유 자원을 변경(쓰기)하는 코드 영역**을 의미한다.

<br>

임계 구역 문제를 해결하기 위해서는 다음 세 가지 요구 조건을 충족해야 한다:

- **상호 배제(Mutual exclusion)**
  - 한 스레드가 임계 구역에서 실행 중이라면, **다른 어떤 스레드도 해당 임계 구역에 진입할 수 없어야 한다.**
  - 공유 자원에 동시에 접근하는 일이 없어야 한다.

- **진행(Progress)**
  - **임계 구역에 실행 중인 스레드가 없을 때**, 임계 구역에 들어가고자 하는 스레드들 중 **누가 진입할지를 유한 시간안에 결정할 수 있어야 한다.**
  - 아무도 실행 중이 아닌데도 진입 결정이 무기한 미뤄져선 안 된다. 

- **한정된 대기(Bounded waiting)**
  - 어떤 스레드가 임계 구역에 들어가기 위해 요청을 했다면, **그 스레드는 유한한 시간 내에 반드시 임계 구역에 들어갈 수 있어야 한다.**
  - 나중에 요청한 스레드들에게 계속 밀려 무한히 대기(기아 현상)해서는 안된다.

## Mutex Locks(뮤텍스 락)

뮤텍스 락은 임계 구역을 보호하고 경쟁 상태를 방지하기 위한 가장 기본적인 동기화 도구이다.

- 스레드는 임계 구역에 들어가기 전에 반드시 `acquire()` 함수로 락을 **획득**해야 하고, 임계 구역을 빠져나올 때 `release()` 함수로 락을 **반환**해야한다.
- `available`이라는 boolean 변수가 락의 가용 여부를 표시하며, 락이 사용 불가능하면 다른 스레드는 봉쇄된다.

<br>

**Mutext Locks 를 사용한 임계 구역 문제 해결 방안**

```java
do {
    acquire(); // 락 획득 (Entry Section)
        // Critical Section (임계 구역)
    release(); // 락 반환 (Exit Section)
        // Remainder Section (나머지 구역)
} while(true);

acquire() {
    while(!available) // 락이 사용 가능해질 때까지 반복 대기
        ; /* busy wait */
    available = false; // 락 획득 (사용 불가로 변경)
}

release() {
    available = true; // 락 반환 (사용 가능으로 변경)
}
```

뮤텍스 락의 단점은 락이 사용 중일 때, 대기하는 스레드가 CPU를 계속 사용하며 락이 풀렸는지 반복해서 확인하는 **바쁜 대기** 방식을 사용한다는 점이다.  

이로 인해 유의미한 작업 없이 CPU 자원이 낭비될 수 있는데, 이를 **스핀락**(Spinlock)이라고 한다.  
 
하지만, 락이 짧은 시간만 유지될 경우에는 스레드를 멈추고 다시 실행하는 문맥 교환 오버헤드가 없기 때문에 오히려 성능에 유리할 수 있다.
